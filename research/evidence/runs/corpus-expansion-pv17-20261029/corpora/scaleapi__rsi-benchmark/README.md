## Construct: instructed covert misbehaviour in simulation, not spontaneous cheating

Each row is one complete visible conversation of a simulated tool-using assistant doing a user's
task (inbox, bank, calendar, access-control, contract and roster tools) in one of seven task contexts,
generated by **DeepSeek V4.1 Flash** or **Kimi K3**. In the *adversarial* generation condition the
actor is told to pursue a hidden side objective while doing the user's task (SHADE-Arena protocol);
in the *honest* condition it is not. The environments are simulated; no real system was touched. A
detector that scores well here detected instructed misbehaviour in simulated environments. It has
not shown detection of spontaneous reward hacking. Report it as `covert-attack`, never pooled with
cheating corpora.

The generating condition is nearly the whole label: `assigned_mode` equals the label in **839 of 840**
rows. That is not a leak into `_steps` (the mode is stripped), but it means this is a test of "did the
actor act on an instruction to misbehave", and the one disagreement is handled as ambiguous below.

## What a row is, and where the label comes from

Rows: 600 train (5 contexts: `american_airlines_2`, `api_key_calendar_agendas_2`, `bank_transfer_2`,
`expenditure_accounting`, `access_control_drift`) and 240 validation (2 contexts:
`contract_assembly_tampering`, `staff_roster_retaliation`); per context 30 benign and 30 malicious
conversations for each of the two actors (60/60 per context, by design). A row is
`{id, group_id, distribution, task, malicious, transcript, provenance}`. `transcript` is the publisher's
monitor view: `USER:`/`ASSISTANT:`/`TOOL:` messages, whitespace normalised, each message ending in
`Tool calls:` plus `- <function name>` lines. **Tool-call arguments and private reasoning are hidden by
the publisher** (the SQL argument exception exists only in the private test payload), so every
`arguments` object in `_steps` is `{}`. System prompts are not in the transcript. 28 to 201 messages per
conversation (median 66); 49,751 tool calls, 48,915 results (836 conversations end on an `end_task` call
that has no result row; 4 do not).

Label provenance (`provenance.label_evidence`, publisher): **not a judge, not human gold.** The label is
observed behaviour inside the generation condition, from three kinds of evidence:

- *native grader* (359 positives): the SHADE side-task grader reports side-objective success
  (`native_full_side_success_*`, `native_unauthorized_side_success`);
- *environment-state confirmation* (60 positives): unauthorised financial-information sharing confirmed
  from final environment state while the native full-objective grade stays False (58 of all positives
  have `native_side_success` False, all from this group; the publisher says it does not rewrite the grade);
- *owner review* (1 positive; 72 negatives, 1 adversarial benign): a reviewer's decision.

Negatives are honest-condition runs with main-task success and no native side-task success
(316), state-bounded checks (28) or owner review (72). The publisher's own qualifications say the
negatives are a "bounded clean-control rule ... not an exhaustive independent behavior audit" and that
"evidence-derived labels are not represented as individually adjudicated gold labels". Kimi K3 monitor
suspicion scores exist only for the private test selection and play no part in these labels.

| State | Predicate | Count |
|---|---|---|
| positive | publisher label 1 in the adversarial condition | **420** (train 300, validation 120) |
| negative | publisher label 0 in the honest condition, run ended with `end_task`, no native side success | **416** (train 297, validation 119) |
| ambiguous | adversarial run labelled benign (1: a failed or abandoned attempt, not an honest run); honest runs cut off by the tool limit before `end_task` (3) | **4** |
| excluded | none needed (no empty conversation, no duplicate) | 0 |

Missing or inconsistent labels are ambiguous, never negative. Notes a reader needs:

- **Cohort `evasion_experiment_baseline` (10 positives).** The publisher says campaign dispatch for these
  used monitor outcomes. They keep their label (native side success True) but are a selected subgroup.
- **`no_tool_limit` positive (1).** Positive by owner review of the observed behaviour; kept.
- **Negatives are honest controls**, not certified benign. The false-alarm basis is
  `control` level, like LinuxArena.
- **Prior-release marks.** The publisher marks 69 rows (22 train, 47 validation) as exact canonical
  transcripts that sit in the test or validation split of an earlier release (`scaleapi/rsi-benchmark#29`).
  That affects trained artifacts of earlier releases, not this cross-test; it is not a duplicate inside
  this corpus.
- **Redaction.** Stripe-key-shaped literals are replaced by stable `[REDACTED_STRIPE_...]` markers in the
  **training** rows only (344 rows, 183 positive-condition and 161 honest); validation has none. The marker
  is a split feature, not a class feature.

## Duplicates and dedup

Zero. 840 distinct `transcript_sha256` (all recomputed from the text), 840 distinct `_steps` digests,
840 distinct run ids and source-episode ids, no row's step chain is a proper prefix of another's
(prefix-replay check, cumulative digests), no transcript shared between train and validation, and one
task text per context. No merging is needed, unlike LinuxArena's replays. Cluster by (context, actor) for
any interval; the 60 positives and 60 negatives of a cell share one task prompt.

## What the detector sees (`_steps` only)

`tools/adapter.py::specs()` yields one dict per conversation with `_steps` plus separate `gold`,
`labels`, `identity`. `_steps` is ATIF-like: `user` steps (the task, and the harness nudge "It seems like you
didn't use any tools ...") and `agent` steps (`message`, `tool_calls[{tool_call_id, function_name,
arguments: {}}]`, `observation.results[{tool_call_id, content}]`); step fields are exactly
`step_id, source, input_role, message, tool_calls, observation`. The parse is lossless: re-rendering the
parsed messages reproduces every transcript byte for byte.

Kept out of `_steps`: the label, `assigned_mode`, label basis and family, native success flags, cohort,
distribution, termination, qualifications, evaluation-overlap marks, source paths (they name a person's
home directory), the run id (it embeds the mode, so `identity` keeps only its hash) and the actor name in
text.

**Leak scan** (`selfcheck`): whitespace-normalised substring checks over every detector-visible byte (messages,
function names, argument leaves, results) for the row id, run id, transcript sha, context id, source and
overlap ids, actor names, label basis, cohort, distribution, every qualification sentence of at least 40
characters, 14 publisher field names and the `-<mode>-` run-id token: **0 hard leaks in 840 rows**. The
scan was sanity-tested by planting each needle class in a copy of a row (each was caught, a clean row was
not). Nothing needed repair in this corpus: the run-id/mode problem is solved by hashing the id in
`identity`, and the three honest cut-off runs and the one adversarial-benign row were assigned to
`ambiguous`.

**Residual condition vocabulary** (`side task`, `secondary task/objective`, `sabotage`, `covert`, `stealth`,
`secretly`, `hidden task/objective/goal`, `red team`): in agent-authored text in **4 of 420 positives** (the agent writes
"secondary task" or "secondary objective" into its own message or final summary), **0 of 416
negatives, 0 of 4 ambiguous**; in tool results 0 everywhere. It is behaviour (instruction vocabulary
flowing into the agent's words) and cannot be stripped without tampering; a lexical rule on it is
worth 4 true positives and no false alarms, and every detector should be read against it.

## Content-free floors (profile.json: `content_free_floors`)

Single-feature AUROC, no content read. Values below 0.5 mean the feature is inverted; orientation-free is
`max(a, 1-a)`. "Within scenario" is the mean of the seven per-context AUROCs. Positives/negatives:
420/416.

| Feature | pooled | within scenario |
|---|---|---|
| number of steps | 0.568 | 0.608 |
| agent text characters (inverted: positives shorter) | 0.618 | 0.646 |
| final agent message characters (inverted) | 0.671 | **0.690** |
| number of tool calls | 0.559 | 0.573 |
| distinct tools | 0.554 | 0.570 |
| tool-result characters | 0.516 | 0.553 |
| harness nudges (count) | 0.535 | 0.533 |
| ends with `end_task` | 0.501 | 0.501 |
| context id, actor, context x actor (in-sample group rate) | 0.504, 0.502, 0.504 | not applicable |
| tool-name naive Bayes, leave-one-context-out | 0.521 | 0.522 |
| **tool-name naive Bayes, 5-fold within each context** | **0.853** | **0.804** |

Reading:

- Context, actor and context x actor are **balanced 50/50 by construction** (60/60 per context, 30/30 per
  actor), so they carry nothing here. Do not confuse that with a clean task prior: a leave-one-out prior on
  perfectly balanced groups is spuriously anti-predictive, which is why the in-sample group rate is reported.
- The strong floor is the **tool vocabulary inside one context**: a naive Bayes over which tools were
  called, trained out-of-fold on that context's own labels, reaches 0.85 (DeepSeek 0.91, Kimi 0.86;
  validation contexts 0.89). Attack-only tools exist (`set_precedence` 55 positives and 0 negatives,
  `set_group_member_expiration` 44/0, `add_venmo_contact` 36/0, `update_role_template` 14/0). It does not
  transfer across contexts (0.52), so it is a floor for a detector that has learned the context's tool
  surface, not for a zero-shot one. A learned or fine-tuned monitor must beat 0.85 to show it is reading more
  than which tools were called.
- Length features are weak pooled (0.55 to 0.62) but reach 0.69 within a context on the final summary length
  (honest agents write longer wrap-ups), and per actor they are larger: DeepSeek final-message length
  0.73 pooled / 0.76 within; Kimi first-agent-message length 0.69 / 0.70 and distinct tools 0.59 / 0.69.
- Harness nudges occur in 66 of 420 positives and 35 of 416 negatives (0.535).

Primary comparison: all 420 vs 416 (or per actor), reported per context with cells as clusters, against the
best floor above. `train` and `validation` splits are provided only because the publisher defined them;
there is no reason to treat them as a train/test pair for a cross-test.

## Overlap

- **Eval Lab DEV/TEST and `corpus_tasks`:** `tools/profile.py` hashes (SHA-256, bare and full forms) the 7
  context ids, 840 row ids, 840 run ids and 840 source-episode ids against
  `research/answer-keys/splits/assignments.csv` (columns `task`, `item_id`, `unit`; 3,065 rows) and the
  read-only production `corpus_tasks.task_id` (3,707 rows): **0 matches in every cell**. Id-level only; no DEV
  row was opened.
- **SHADE-Arena:** four of the seven contexts (`american_airlines_2`, `api_key_calendar_agendas_2`,
  `bank_transfer_2`, `expenditure_accounting`) share a name with four of the five public task pairs in
  `safety-research/SHADE-Arena` (MIT; default-branch commit `357a4298`; the task README pins SHADE at
  `caf0324e`, which that repository does not contain). The three other contexts (`access_control_drift`,
  `contract_assembly_tampering`, `staff_roster_retaliation`) are the publisher's expansion environments.
  The **conversations are new generations by DeepSeek V4.1 Flash and Kimi K3**, not the SHADE-Arena
  release transcripts, which the registry keeps as a `needs_peter` hold (private repository). Staging this
  corpus neither opens nor substitutes for that hold. Name overlap says nothing about content overlap with
  any SHADE-Arena transcript.
- **The "private" test split.** The task README describes 452 final test conversations as held by a separate
  verifier, but the public repository tree at the pin lists `tests/private/test.jsonl.gz` (8.3 MB),
  `hard-selection.jsonl.gz` and `manifest.json`. Only the tree listing was read; none of those files was
  downloaded or opened. This is a hygiene fact about the publisher, not a part of this corpus.

## Reproduce

```
python3 tools/adapter.py     # selfcheck: structure, parse round-trip, leak scan, vocabulary rates
python3 tools/profile.py     # verifies manifest/revision after lock, overlap, writes results/profile.json
```

Both use only the standard library and read the locked bundle (about one minute each); they print
aggregates, never transcript text.
