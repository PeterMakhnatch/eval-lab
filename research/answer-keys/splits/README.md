# Answer-key splits and exposures

Rule (FOCUS.md): never tune on the split you report, and name the split of every
number. Tuning is allowed only on `dev`; `test` and `heldout` are the reported splits
and mean the same thing (the trace keys say `test`, the task keys say `heldout`).

| file | what | edited by |
|---|---|---|
| `assignments.csv` | Every item of every key: `key_id, item_id, task, unit, split, expected_verdict, exposures` | generated by `guard.py` |
| `report.md` | Split counts per key, task names that are `dev` in one place and reported in another, and exposure counts | generated by `guard.py` |
| `exposure.jsonl` | Who was tuned on, or read outputs of, which items | by hand, one record per exposure |
| `guard.py` | Writes the two generated files; `--check` fails on a stale file, a unit straddling splits, a bad exposure reference, or a scoreboard row that scores tuned items on a reported split | Classifiers |

Run `uv run python research/answer-keys/splits/guard.py` after changing a key or
`exposure.jsonl`. `tests/test_answer_key_splits.py` runs the same checks in CI.

## Units

- A unit is a set of items linked by the same `subject.task_id` or by a pair. Each key
  assigns splits per unit, so a unit never spans two splits:
  - task for trace-paired-v1;
  - instance for trajectory-judge-400;
  - benchflow pair for breaker-bench-v1.
- Across keys, tasks are compared by bare name, without the pin or benchmark prefix.
  A name that is `dev` in one key and reported in another is listed in `report.md`.
  It only matters if the same system tunes on one side and reports on the other.

## Recording an exposure

Add a line to `exposure.jsonl` whenever a system is tuned on key items, or its
held-out outputs are read before a change.

| field | contents |
|---|---|
| `kind` | `tuned` or `inspected` |
| `applies_to` | List of `{agent, system_prefix?, from?}`. These match the scoreboard `agent` column, a `system` prefix, and a first `date_utc` day. |
| item selection | One or more of `tasks` (bare names, any key), `items` (`{key: [item_id]}`), `items_file` (`{key: path}`, one item or trial id per line), `where` (`{key: {field: value}}`) |
| `acknowledged_rows` | Optional list of `{key_id, system_prefix, how: excluded|disclosed, reason}` |

How the guard judges a scoreboard row on a reported split that contains items its
system was tuned on:
- With no acknowledgement, the row is an error.
- With `how: excluded`, the guard checks the claim is possible: the row must leave at
  least that many items unmeasured.
- With `how: disclosed`, or when the exposure is only `inspected`, the guard prints a
  warning.
