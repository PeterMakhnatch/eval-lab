# Run Atlas retrieval: profiling and discarded batching experiment

**Question:** Can repeated in-process retrieval be accelerated without changing any admission, sealing, screening, ranking or output? **Result:** no repeatable 15% gain was established. The production implementation is unchanged. `candidate.patch` records the discarded experiment, not a shipped implementation.

The store was the 4,207,423,488-byte read-only SQLite backup at `/private/tmp/ps2/store.sqlite`; baseline commit `2dea8b9d99b9a312886193cca3989295e36391fe`. No model, Docker, or cloud store was used. All measurements use a `CorpusRegistry` from the respective checkout. Profile tables give the top five cumulative CPU entries for each mode, plus unprofiled cold/warm CPU and wall medians (seven samples each); cold creates a fresh database/retriever but does not flush the OS cache. cProfile's per-call CPU timer has substantial overhead, cumulative entries overlap, and profiling and other local work overlapped.

The initial profile showed repeated facet-screen regex work inside `_retrieval_facets`. The candidate batches the exact same joined string values through the existing `_sealed_texts` function, without memoizing verdicts or changing the screen. An interleaved n=7 old/new experiment, with other local work running, initially showed warm cluster+anchor CPU medians **0.138648 → 0.107469 s** and cluster **0.256545 → 0.186680 s**; facets went **0.556950 → 0.631279 s**. The cleanly separated focused recheck did not reproduce the apparent gain: cluster+anchor warm medians **0.129309 → 0.139042 s**, with first-call medians **0.342358 → 0.418240 s**. Each of seven interleaved alternating-order process pairs reported the median of five repeated calls after its first. Worktree setup/discovery warmed some database state before each first call, so these are not cold-object measurements. System contention and CPU sample variability remain visible; do not treat the first experiment as proof of a 15% gain.

The candidate and baseline produced byte-identical canonical full results for 50 distinct DEV-goal queries across lexical, facets, cluster, anchor, and cluster+anchor. Five queries used a screened-out facet as anchor and five used un-faceted anchors. The admitted store contained only **one** distinct screened-out run, so the five withheld-anchor cases reuse it with different goals; 3,309 admitted runs lacked facets. In addition 24 QA replies matched after dropping `meta`, across all **14** command names in the actual `CALLS` registry; four were identical refusals (including export, steps, and scan without required input). The request named 17 call types, but this checkout defines 14. These are equivalence checks of the discarded candidate, not proof about untested inputs.

`profile.py`, `compare.py`, `focused.py`, `identity.py`, and `qa_compare.py` capture the protocols. For a reproduction, use separate checkouts at the baseline, apply `candidate.patch` only to the candidate checkout, set the paths in the scripts, and use an isolated environment. Identity scripts write full replies only under `/private/tmp/ps5`; committed results contain counts and timings, not replies. `results.json` includes the focused raw CPU samples. The ordinary focused tests passed (253 tests); no new regression test was added because the candidate was discarded and no behavior was changed.
