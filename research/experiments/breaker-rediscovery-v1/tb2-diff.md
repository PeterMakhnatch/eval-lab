## 5. Breaker-Reachable Candidate Identification

A task is marked `breaker_reachable_candidate = true` if and only if `tests/` (verifier logic) or answer-material exposure in `environment/` changed between `69671fb` and `7131e43` in a **strengthening** direction (closing a false-positive or answer-leak path that a container breaker could exploit to pass TB2 `69671fb` while failing or being blocked on TB2.1 `7131e43`):

- **`fix-git` (`breaker_reachable_candidate = true`, `change_kind = anti_hack_or_verifier_strengthening`)**:
  - **TB2 (`69671fb`)**: `environment/Dockerfile` copies `resources/` (`/app/resources/patch_files/{about.md,default.html}`) and `setup.sh` into `/app` and leaves them on disk after `RUN bash /app/setup.sh`. Furthermore, `tests/test_outputs.py` grades by running `compare_file_hashes("/app/resources/patch_files/...", "/app/personal-site/...")` against those readable, candidate-writable files (`task_answer_in_env` + `task_writable_grader`).
  - **TB2.1 (`7131e43`)**: `environment/Dockerfile` runs `RUN bash /app/setup.sh && rm -rf /app/resources /app/setup.sh`, and `tests/test_outputs.py` replaces `compare_file_hashes` with `check_file_hash` against hardcoded MD5 digests (`0273104059c6bf524e767b8847b22946` and `0f879389f66640f45316e393a71c5f2f`).
  - **Digests**: `old_verifier_digest = sha256:87ede52989f2f0e01abeb494960f66f248c70fc9a16b605af4b0561b5b91077d` $\to$ `new_verifier_digest = sha256:0e3a003d01515bbac8e8715b09fcca9b9004e6b72f3f8fcc8b5cc532ee9a32a3`.
- **Why the other 9 `verifier_digest`-changed tasks are `breaker_reachable_candidate = false`**:
  - `caffe-cifar-10`, `hf-model-inference`, `polyglot-c-py`, `polyglot-rust-c`, `sam-cell-seg`, `train-fasttext`: all **relaxed** over-strict or fragile assertions (accepting CMake builds, accepting HuggingFace cache layout, allowing compiled binaries alongside source, removing a redundant `isinstance` check, switching from `fasttext-wheel` `> 0.62` to self-contained `fasttext` CLI `>= 0.62`).
  - `configure-git-webserver`: fixed a false-negative verifier bug where `tests/verify.sh` used `expect` with hardcoded password `"password"` for user `git` despite `instruction.md` stating SSH auth was pre-configured.
  - `install-windows-3.11`: removed the `has_vga` cmdline check, skipped zombie QEMU PIDs, and added an explicit `Path("/tmp/qemu-monitor.sock").is_socket()` check with error message on the `monitor_socket` fixture that `test_windows_keys_with_visual_feedback` already connected to via `socat UNIX-CONNECT:/tmp/qemu-monitor.sock`.
  - `sanitize-git-repo`: split 5 `FAKE_*` token literals into `'prefix' + 'suffix'` strings with identical Python AST runtime values.
- **Why `query-optimize` and `mteb-retrieve` are `breaker_reachable_candidate = false`**:
  - Neither task modified `tests/` (`verifier_digest_changed = false`). In `query-optimize`, `chmod 444 /app/oewn.sqlite` and `test_check_for_db_modifications()` (SHA-256 check) were already present in TB2 `69671fb`; TB2.1 only disclosed that existing rule in `instruction.md` and raised `verifier.timeout_sec`. In `mteb-retrieve`, `tests/test_outputs.py` is unchanged (`expected = "MTEB: Massive Text Embedding Benchmark"`); TB2.1 only clarified in `instruction.md` that `mteb==1.36.8` must be used and pinned `transformers==4.48.3` in `Dockerfile`.
