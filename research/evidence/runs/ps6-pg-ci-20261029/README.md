# PostgreSQL fixture recovery and CI probe

Question: does the next test session reclaim a PostgreSQL fixture after pytest is killed, and are PostgreSQL cases executed on GitHub Actions?

`measure.py`, run from the repository root with the locked virtual environment and PostgreSQL binaries on PATH, starts a fixture, waits until a test is executing, kills pytest with SIGKILL, and runs the same test again. On origin/main the first postmaster and directory remained; with the change both were gone. One trial per version; the script stops the baseline orphan it creates. The local PostgreSQL selection passed 47, skipped 0; all 155 cloud-trace database tests passed. These are behavioral counts, not performance estimates.

The temporary probe on PR #1596, run 40950882968, executed the binary diagnostic and a `-n 0 -rs -k postgres` selection successfully, but GitHub would not serve the running job's logs (HTTP 404); pass/skip counts, binary discovery and skip reasons were therefore not observable without waiting for the full job. The probe was removed. CI behavior is unchanged rather than adding an unverified installation or PATH change. Prior completed CI run 40948505684, job 123710072839, reported 10,924 passed and 374 skipped overall, with 364.76 seconds for pytest; those skips cannot be attributed to PostgreSQL from that summary. CI PostgreSQL counts and wall-time delta remain unknown.

The sweep never signals unmarked legacy directories. It reaps legacy directories only when their same-user PID file names their data directory and the PID is dead. New fixture directories use an exclusive lock, a same-user marker and recorded postmaster PID and start time; a live process is stopped only after those and its command line match. Active sessions retain the lock. Unverifiable or incomplete startup states are left alone, including a kill between server startup and recording identity; SIGKILL itself cannot run atexit. Normal finalization and atexit attempt cleanup, and the next session recovers a verified orphan from a killed active test. The safety checks intentionally favor leaving a directory over signaling an unrelated process.
