## QuixBugs → Harbor Adapter

## Overview

This adapter turns the pinned [QuixBugs](https://github.com/jkoppel/QuixBugs) benchmark into 80 deterministic Harbor repair tasks: 40 algorithms in Python and the same 40 in Java. Each task starts with one upstream one-line defect, exposes only the defective implementation and its toolchain to the agent, and scores `1` only when the separate upstream test suite passes.

The source is pinned to commit `4257f44b0ff1181dedaedee6a447e133219fcebf` and is MIT licensed. No programs are excluded: `40 programs × 2 languages = 80 tasks`. The adaptation splits the two languages into independent tasks, puts tests and corrected implementations outside the agent environment, converts corrected Java package declarations for the task layout, and adds deterministic Docker/Harbor configuration. Generated tasks are committed under `adapters/quixbugs/generated/`.

## What is QuixBugs?

QuixBugs is a multilingual program-repair benchmark based on classic algorithm challenges from the Quixey Challenge. Each implementation contains a defect on one line, with Python and Java versions, tests, and corrected implementations. It was designed to compare repair techniques across languages. The original benchmark and follow-up studies report whether repair systems produce test-suite-passing (plausible) and, when manually assessed, semantically correct patches. See [QuixBugs: A Multi-Lingual Program Repair Benchmark Set Based on the Quixey Challenge](https://github.com/jkoppel/QuixBugs/blob/master/quixbugs.pdf) and [A Comprehensive Study of Automatic Program Repair on the QuixBugs Benchmark](https://arxiv.org/abs/1805.03454).

The Harbor reward is narrower: binary upstream-test success for one program-language task. Passing is evidence of compatibility with the supplied tests, not proof of semantic equivalence for all inputs.

## Adapter Features

- A self-contained `uv` package created with `harbor adapter init`; the repository root dependency files are not modified.
- Exact source pinning and validation. The default command fetches the pinned commit into a temporary directory and removes it after generation.
- Stable IDs of the form `quixbugs-<language>-<program>` and task names of the form `quixbugs/quixbugs__<language>__<program>`.
- Full generation plus `--output-dir`, `--limit`, `--task-ids`, `--language`, and `--overwrite` controls. Generation is staged, and `--overwrite` replaces the complete output dataset only after generation succeeds.
- Python 3.13/pytest and Java 11/Gradle 8.10.2/JUnit 4 containers. All base images are pinned by digest; Python packages are hash-locked; JUnit/Hamcrest jars are checksum-verified and used by Gradle offline.
- Separate Harbor verifiers: upstream tests and Oracle source are never copied into the evaluated agent environment. Harbor transfers only the target source artifact into a verifier-owned, read-only project and runs candidate code as a non-root user.
- Deterministic `generation_manifest.json` output with the source ref, selected IDs, task count, and content-tree SHA-256. Copied Python text and Java JUnit inputs are normalized only to LF with one trailing newline so generated bytes survive Git checkouts unchanged.
- Binary rewards, per-test output in `/logs/verifier/test-output.txt`, and bounded verifier timeouts.

## Generated Task Structure

```text
adapters/quixbugs/
├── generated/
│   ├── generation_manifest.json
│   └── quixbugs-<language>-<program>/
│       ├── LICENSE
│       ├── task.toml
│       ├── instruction.md
│       ├── environment/
│       │   ├── Dockerfile
│       │   └── ...                    # target source and language build files
│       ├── solution/
│       │   └── solve.sh               # pinned corrected implementation
│       └── tests/
│           ├── test.sh
│           └── ...                    # hidden upstream pytest or JUnit inputs
├── src/quixbugs/
│   ├── adapter.py
│   ├── main.py
│   └── task-template/
├── pyproject.toml
└── uv.lock
```

The Python agent sees `/app/python_programs/<program>.py`. The Java agent sees `/app/src/main/java/java_programs/<PROGRAM>.java`. Harbor runs verification in a separate image and transfers only that source file; verifier tests, runners, dependency locks, and build configuration are not taken from the agent container.

## Run Evaluation / Harness

Run commands from the `harbor-experiment-lab` worktree root after generating the dataset. The checked-in config is intentionally model-free and uses the local Oracle with at most two concurrent trials:

```bash
harbor run -c adapters/quixbugs/run_quixbugs.yaml
```

For an individual local control:

```bash
harbor run   -p adapters/quixbugs/generated/quixbugs-python-gcd   -a oracle -k 1 -n 1   -o runs/quixbugs-adapter/smoke
```

No model or billed provider is configured. A model-backed evaluation must be an explicit operator choice rather than a default path.

## Usage: Create Task Directories

From a clean checkout, install only the adapter's locked environment and regenerate all 80 tasks:

```bash
cd adapters/quixbugs
uv sync --frozen
rm -rf generated
uv run quixbugs --output-dir generated
```

The default fetch verifies exact Git commit `4257f44b0ff1181dedaedee6a447e133219fcebf`. A pre-existing checkout is supported only when it is clean and its `HEAD` is that commit:

```bash
uv run quixbugs   --source-dir /path/to/QuixBugs   --output-dir generated   --overwrite
```

Bounded generation examples:

```bash
# First five IDs in stable lexicographic order
uv run quixbugs --output-dir /tmp/quixbugs-five --limit 5

# Exact variants; a bare name such as gcd selects both languages
uv run quixbugs --output-dir /tmp/quixbugs-selected   --task-ids quixbugs-python-gcd quixbugs-java-minimum_spanning_tree

# A complete language split
uv run quixbugs --output-dir /tmp/quixbugs-python --language python
```

Any non-empty output directory is rejected unless `--overwrite` is supplied. Overwrite is whole-dataset replacement, not a merge: a bounded selection replaces the old output with exactly that selection and its matching manifest. Generation occurs in a sibling staging directory; an error before the swap leaves the existing output unchanged.

To verify clean reproducibility without touching the committed tree:

```bash
rm -rf /tmp/quixbugs-clean-regeneration
uv run quixbugs --output-dir /tmp/quixbugs-clean-regeneration
diff -qr generated /tmp/quixbugs-clean-regeneration
```

The expected full manifest records 80 tasks and tree digest `894c6cfd59cc5513c75fa758a0092420a8b24befdeedc5fb46a9f91b8dc60445`.

A defensible parity experiment is deferred until all of the following can be fixed in advance:

1. Select a published repair system, exact revision, original subset, search budget, and repeated-run protocol.
2. Reproduce that system in the original QuixBugs harness and archive per-task outputs.
3. Run the same system, inputs, tests, budget, and number of repetitions through Harbor.
4. Compare per-task test-suite success and manually assessed correctness, report uncertainty and failures, and publish both run configurations and artifacts.

`parity_experiment.json` therefore contains a model-unset, zero-run deferred record rather than claiming an unmatched comparison.

## Notes & Caveats

### Local verification evidence

All 80 task configurations parsed, all 160 generated shell scripts passed `bash -n`, and every starting and Oracle source compiled (40 per language). On 2026-08-13 with Harbor `0.21.0` and local Docker, the following five-task sample was exercised with concurrency `2`:

- `quixbugs-python-gcd`
- `quixbugs-python-breadth_first_search`
- `quixbugs-python-minimum_spanning_tree`
- `quixbugs-java-gcd`
- `quixbugs-java-minimum_spanning_tree`

Oracle command (three attempts per task):

```bash
harbor run -p adapters/quixbugs/generated   -i quixbugs-python-gcd   -i quixbugs-python-breadth_first_search   -i quixbugs-python-minimum_spanning_tree   -i quixbugs-java-gcd   -i quixbugs-java-minimum_spanning_tree   -a oracle -k 3 -n 2 -q   -o runs/quixbugs-adapter/separate-oracle-final
```

Result: `15/15` completed, `0` exceptions, all rewards `1.0`, mean `1.0`.

No-op command: use the same five `-i` filters and replace the final agent options with:

```bash
-a nop -k 1 -n 2 -q -o runs/quixbugs-adapter/separate-nop-final
```

Result: `5/5` completed, `0` exceptions, all rewards `0.0`, mean `0.0`. Structured evidence and local result hashes are recorded in `verification_evidence.json`; raw jobs stay in the ignored worktree `runs/` directory.

A two-task adversarial regression replaced the Oracle solution with the two original review exploits: creating `/app/pytest.py` in the Python agent container and replacing `/app/build.gradle` in the Java agent container. Because neither file is a declared artifact and the verifier owns its runner/build configuration, both trials completed with reward `0.0` and no exception. This specifically guards the reported configuration-file bypasses; the target implementation itself remains untrusted code constrained by the verifier container, non-root execution, read-only inputs, and Harbor timeouts.

Generation regressions also confirmed that a bounded overwrite leaves no stale tasks, an injected mid-generation failure preserves the prior dataset, and a fresh network regeneration is byte-identical.

### Three informative canaries

1. **`quixbugs-python-gcd`** checks the minimal Python path, JSON testcase loading, Oracle replacement, and separate pytest verifier.
2. **`quixbugs-python-breadth_first_search`** exercises graph fixtures via the hidden `Node` helper and a defective non-terminating branch, so it also checks pytest timeout containment.
3. **`quixbugs-java-minimum_spanning_tree`** checks Java package conversion, Gradle/JUnit, automatic inclusion of both `Node` and `WeightedEdge`, and collection-valued assertions.

### Limitations

- Upstream tests are hidden from the evaluated process by Harbor, but they are public in the upstream repository; this is an adaptation for reproducible evaluation, not a claim of secret benchmark data.
- Rewards measure the supplied test suite. Test overfitting or behavior outside covered inputs remains possible.
- Python follows the upstream default of skipping explicitly slow cases. The adapter adds a per-test-file timeout for containment.
- Initial generation and image builds require network access for the pinned Git source, digest-pinned base images, hash-locked Python packages, and checksum-verified Java jars. Java test execution itself uses Gradle offline. Subsequent builds may use Docker caches.
- The default full config uses the Oracle as a consistency control. It is not an agent capability result.

- Git
- [`uv`](https://docs.astral.sh/uv/)
- Harbor `0.21.0` or a compatible newer version
- Docker Desktop/Engine with at least 2 GB available per task
- Network access for the first source fetch and image/dependency pulls

Install the adapter environment independently of the repository root:

```bash
cd adapters/quixbugs

```

## Troubleshooting

- **Pinned source rejected:** `git -C /path/to/QuixBugs rev-parse HEAD` must equal `4257f44b0ff1181dedaedee6a447e133219fcebf`, and `git status --porcelain` must be empty.
- **Output already exists:** remove the disposable output or pass `--overwrite`. Regeneration never silently replaces tasks.
- **No task matched `-i`:** Harbor dataset filters use directory IDs such as `quixbugs-python-gcd`, not the namespaced task name from `task.toml`.
- **Java dependency failure:** verify Maven Central access during the verifier-image build. The image downloads fixed JUnit/Hamcrest URLs, rejects checksum mismatches, and runs Gradle tests offline afterward.
- **Docker resource failure:** keep `-n 2` or lower; the worktree policy forbids concurrency above two.
- **Inspect a failure:** run `harbor view runs/quixbugs-adapter/<control>` and open the trial's verifier `test-output.txt`.
